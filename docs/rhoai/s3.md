# S3 distribution and the optional ODF dependency

The default remains the small HTTP publisher. For S3, the same trusted Job
encrypts the pinned Qwen files, uploads one `qwen.tar` to a unique release path,
then reads it back and checks its SHA-256 before activation. RHOAI's existing
initializer downloads and extracts the archive inside the confidential VM.
CDH/Trustee supplies the JWE key, the streaming derivative decrypts onto the
guest's LUKS filesystem, and vLLM and HTTPS chat run as before.

S3 credentials authorize access to **ciphertext only**. They are ordinary
Kubernetes Secrets supplied by Vault/External Secrets, not Trustee resources.
The model, disk, registry and chat private keys remain bound to attestation.
Only the initializer mounts the reader credentials; neither vLLM nor chat does.
The guest policy measures the endpoint, region, paths and exact trusted CA
bytes, but deliberately excludes credential contents so credentials can rotate.

## Choose storage before bootstrap

Use either:

| Setting in `global.rhoai.storageProvider` | Result |
|---|---|
| `external` (default) | No ODF installation; HTTP or an administrator-provided S3 endpoint |
| `odf` | Red Hat ODF operator plus a standalone Multicloud Object Gateway (MCG), private model bucket and separate accounts |

The ODF overlay pins `odf-operator.v4.22.6-rhodf` on `stable-4.22` from
`redhat-operators`. Review OCP/ODF compatibility before changing this pin.
It creates a `StorageCluster` with
`multiCloudGateway.reconcileStrategy: standalone`, a PVC-backed `BackingStore`,
a `BucketClass`, an `ObjectBucketClaim`, and two `NooBaaAccount` resources.
It does not install a Ceph storage cluster. Existing block storage must supply
the MCG database and backing-store PVCs.

Red Hat's [ODF 4.22 standalone MCG installation guide](https://docs.redhat.com/en/documentation/red_hat_openshift_data_foundation/4.22/html/deploying_openshift_data_foundation_on_any_platform/deploy-standalone-multicloud-object-gateway)
lists at least three worker/infrastructure nodes. The single-node test site is
a development deployment, **not a supported or highly available ODF topology**.
The example's one-volume backing store is deliberately minimal; size, placement,
availability and backup require a production storage design.

Set `storageProvider: odf` beside the site's existing `rhoai.site` in
`install.yaml`. Optionally add `values-object-storage.yaml` in that site:

```yaml
objectStorage:
  storageClass: lvms-vg1
  backingSize: 100Gi
  prefix: qwen3-0.6b
```

The chart requests 1 GiB and allows 2 GiB for the model backing-store agent,
with a two-CPU limit. The operator's minimal 400 MiB agent limit was insufficient
for the tested multipart model upload. Tune `objectStorage.backingResources`
for your workload; database and gateway sizing remain product-managed.

Do this before the installation runbook's bootstrap/commit/install steps.
Approve the initial CoCo plans first. Wait for the `baremetal`, `sandbox` and
`nvidia-gpu` applications to be Synced/Healthy and for
`scripts/rhoai-demo.sh preflight` to pass, then review and approve ODF's initial
manual InstallPlan. This keeps ODF's webhook and dependency installation out of
the runtime-reboot window. A dependency InstallPlan in `Failed` is a failed
installation, even if the primary ODF CSV subsequently becomes `Succeeded`.
The expected initial CSV is `odf-operator.v4.22.6-rhodf`; the product operator
installs its matching dependencies. Wait for `rhoai-object-storage` to become
Synced/Healthy and for `job/rhoai-object-storage-policy` to complete in
`openshift-storage`. Do not approve an unreviewed upgrade.

For the single-node lab, `testing/cluster-01/values-site.yaml` also sets
`runtimeTimeouts.maxPods: 500`. This becomes part of the existing GPU
`KubeletConfig`. It prevents the complete operator stack exhausting the
250-pod default during bootstrap. It is a site capacity choice, not a generic
requirement; allow the node configuration to finish before proceeding.

## Enroll S3 credentials before publishing

Follow the main runbook through initializer build and model-key enrollment.
Keep `RHOAI_INSTALL_VALUES`, `STATE_DIR`, `KUBECONFIG` and `HELM` set.

For the pattern-provisioned ODF bucket:

```bash
scripts/rhoai-s3.sh odf
```

The helper waits for the bucket, accounts and policy Job, reads the generated
credentials without displaying them, enrolls them into Vault and writes only
public configuration to the site's `values-distribution.yaml`.
The generated bucket name, service endpoint, region and public service CA are
site-specific. A random release ID is retained in private state for retries.
Set a new `S3_RELEASE_ID` for a new encryption/publication attempt after an
archive has already been uploaded; JWE encryption generates new random bytes.

For an existing S3-compatible endpoint, provision two distinct identities and
the permissions below, then supply private standard AWS SDK credential files:

```bash
export S3_ENDPOINT=https://s3.example.org
export S3_URI=s3://models/qwen3-0.6b/UNIQUE_RELEASE_ID/qwen.tar
export S3_PUBLISHER_CREDENTIALS_FILE=/secure/path/publisher.credentials
export S3_READER_CREDENTIALS_FILE=/secure/path/reader.credentials
export S3_REGION=us-east-1
# Optional for a private CA; omit for a publicly trusted certificate.
export S3_CA_FILE=/secure/path/object-storage-ca.crt
scripts/rhoai-s3.sh external
```

Each credentials file has a single `[default]` profile with
`aws_access_key_id`, `aws_secret_access_key` and, if needed,
`aws_session_token`. The helper refuses identical reader/writer credentials.
Vault administrator access uses the normal pattern bootstrap handoff or an
explicit private `VAULT_ADMIN_TOKEN_FILE`. No credential enters Git.

The ODF policy hook uses the **OBC owner credential only** to configure the
bucket policy. It grants both accounts `ListBucket`, `GetBucketLocation` and
`GetObject` under the model prefix; only the publisher gets `PutObject`,
`AbortMultipartUpload` and `ListMultipartUploadParts`. Neither gets object
deletion or bucket-policy administration. Bucket listing exposes ciphertext
names; this is a dedicated model bucket. Account creation is disabled for both.
The initializer needs its bucket probe/list calls even for one exact object URI.
For ODF 4.22 the policy uses the generated account `ARN` fields, not the
Kubernetes CR names. Each account also specifies the backing store as
`default_resource`, as required by its S3-access API even when bucket creation
is disabled.

## Publish, measure, activate and verify

```bash
export MODEL_KEY_FILE="$STATE_DIR/model-key.json"
scripts/rhoai-demo.sh publish
scripts/rhoai-prepare.sh
scripts/rhoai-configure-owner.sh ready
# Review, commit and push the public site files to the watched branch.
```

Do not push only `values-distribution.yaml` over a running HTTP deployment:
publish first, then prepare and activate its matching measured Qwen/Trustee
values together. Preparation requires the verified publication receipt for the
exact selected URI. The ODF/S3 setup helper preserves all model, LUKS and chat
keys/certificates; rerunning key enrollment is unnecessary when migrating a
working installation.

In S3 mode the Job uses a generic ephemeral PVC for trusted plaintext/encryption
workspace, verifies the uploaded bytes by reading them back, saves
`STATE_DIR/publication.json`, and is deleted after success so Kubernetes removes
its workspace PVC. Deletion is not secure erasure: use trusted publisher storage.
Failed Jobs retain workspace for diagnosis; remove them explicitly after review.
No persistent HTTP Deployment or Service is rendered in S3 mode. A retained
HTTP publisher PVC from a migration is removed separately after acceptance.
The two application owners enable Argo pruning for obsolete configuration and
HTTP resources; the PVC retention annotations still prevent automatic data
deletion. A completed old HTTP publication Job is administrator-owned and can
also be removed after migration.

The uploader refuses to overwrite an existing release with different bytes.
This is a client-side collision guard, not S3 Object Lock or an atomic
multi-writer guarantee. Use unique release paths and one trusted publisher.
Authenticated JWE tags and the pinned plaintext inventory are still checked
inside the VM.

The resulting API contains:

```yaml
model:
  uri: s3://GENERATED_BUCKET/qwen3-0.6b/RELEASE_ID/qwen.tar
  confidential:
    enabled: true
    resourceId: kbs:///default/rhoai-qwen-secrets/model-key
```

Automatic initializer injection remains disabled to preserve LUKS-first ordering.
The explicit initializer gets `AWS_ENDPOINT_URL`, `AWS_DEFAULT_REGION`,
`AWS_SHARED_CREDENTIALS_FILE`, `S3_USER_VIRTUAL_BUCKET=false` and
`S3_VERIFY_SSL=true`. With a private CA, its verified in-memory CA copy is
selected through `AWS_CA_BUNDLE`. No certificate verification is disabled.
CA or endpoint changes require regenerating initdata and the Trustee binding.

Run the main HTTPS/browser verification, then replace the entire confidential
pod and verify the same encrypted PVC is reused. For a fresh-download test,
set a new `storage.claimName` in `STATE_DIR/site-overrides.yaml` before preparing;
otherwise a valid persisted model intentionally skips the download. Keep the
previous claim until the migration succeeds.

Test reader write denial, invalid credentials, an untrusted CA, corrupted
ciphertext and changed guest attestation:

```bash
tests/rhoai/s3_cluster.sh
tests/rhoai/reject_unapproved_guest.sh
```

The S3 negative test runs in the trusted publisher namespace using the stock
Red Hat initializer image: it tests product download failures and rejects a
modified small JWE file taken from the actual published tar. It temporarily
imports the reader credential through ESO and removes its test resources after
success. It does not modify the published object. The separate streaming test
checks the derivative's large-file memory behavior and authentication failure.
The [test-site record](../../testing/cluster-01/README.md)
distinguishes observed results from untested hardware/support claims.
